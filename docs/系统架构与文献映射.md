| 模块 | 架构出自 | 搬什么 | 本项目的优化 |
|---|---|---|---|

## 3. 检索与生成的关键实现细节

### 3.1 A0：OpenStax 与 SciQ 的数据准备

**前提待确认（P0）**：官方项目描述写明「数据集：导师提供」且面向高等教育，而 SciQ 为中小学难度的众包科学选择题。改用公开数据属于范围变更，须经导师确认。

**OpenStax 侧**

1. 选定教材与**版本号**（教材会改版，版本必须记录）
2. 解析、清洗、章节化，保留 `source / page / char_start / char_end`
3. 记录 `parser_version` 与 `document_hash`，防止字符偏移漂移

**SciQ 侧**

1. 学科分类（SciQ 本身无学科标签）
2. 与 OpenStax 章节匹配
3. **Evidence Alignment**：把 SciQ 的 `support` 段落定位到 OpenStax 语料的 char span
   - 方法：embedding 相似度粗定位 + 模糊字符串匹配精定位
   - **必须人工验证一个子集的对齐准确率**——对齐错则 D1 的 Hit@K 全部失真
4. **Dev / Test 按章节或概念组隔离，禁止随机切分**——同一章节会产生高度相关的题目，随机切分造成内容泄漏

> **⚠ 待修（本版未改）：Unanswerable 集合的构建逻辑不成立。**
>
> 当前流程把「support 无法对齐」直接判为 unanswerable，这个推论不成立。对不上可能是因为 SciQ 使用了旧版 OpenStax、support 来自另一部教材、表述经过改写、或匹配算法失败——**原 support 不存在不等于整个知识库无法回答**。SciQ 的题目来源不限于单一 OpenStax 教材。
>
> 正确流程应为：support 对不上 → `Unresolved Pool` → 检索整个 OpenStax 知识库 → 人工确认 → 确有证据则归 Answerable，确无证据才归 `Verified Unanswerable`。只有 `Verified Unanswerable` 可进入 D5。
>
> 本版按团队决定暂缓修改，**冻结前必须补上**。

### 3.2 D2：三层拆分与固定输出格式

SciQ 是选择题，有正确选项。但**选对选项不等于解释正确**：

```text
final_choice: B        ← 正确
explanation: 错误推理   ← 仍然有问题
```

因此 D2 必须拆成三层，各自的评价方式与成本不同：

| 层 | 评价方式 | 覆盖范围 |
|---|---|---|
| **Answer-choice Accuracy** | 与 SciQ 正确选项自动比对 | **全量** |
| **Explanation Correctness** | 人工抽样，或 claim-level 评价 | 分层样本 |
| **Groundedness** | 归 D4 的支持性评价 | 分层样本 |

C7 的输出格式因此固定为：

```json
{
  "final_choice": "B",
  "explanation": "...",
  "citations": ["chunk_17", "chunk_22"]
}
```

固定格式同时使 C8 的引用完整性检查可以纯字符串实现。

**注意**：文档中不得再出现「自动 correctness」这一模糊说法，只能写 **Answer-choice Accuracy**。

### 3.3 A3 Evidence Role：自建 taxonomy，先试标再冻结

六类，2-2-2 梯度：

```text
Beginner      → definition,  example
Intermediate  → comparison,  application
Advanced      → derivation,  boundary
```

**报告中的定位表述**：

> 本项目设计了一套受 Bloom taxonomy 与教育内容结构启发的 pedagogical evidence-role taxonomy。

不可写成已有理论验证的既成体系——六个角色并不直接等同于 Anderson & Krathwohl 的知识维度。

**冻结前必须先试标**：

1. 抽 100–200 个 chunk 试标
2. 检查类别是否严重不平衡
3. **重点检查 `comparison` 与 `application` 是否经常混淆**
4. 双人标注 20%，报告 Cohen κ 或 Krippendorff α
5. 一致性不足 → 修订定义 → 重新试标
6. 通过后方可冻结，再做全语料 LLM 批标 + 人工验证子集

评估用 per-role Precision / Recall / F1 + Macro-F1 + Micro-F1（类别不平衡，不能只报 accuracy）。

### 3.4 C4 Level-Aware Reranking 评分公式

原设计为加法，但 BM25 分数无上界而 Dense 余弦在 0–1，同一权重在两者上相差一个数量级。修正为归一化后的单旋钮，**并直接在主公式中使用 `λ_eff`**：

```text
λ_eff = λ × confidence

final = (1 − λ_eff) · norm(retrieval_score)
      + λ_eff · role_match(level)
```

1. `λ = 0` 即为「关闭检索侧个性化」，开关变成同一参数的取值
2. 可扫 λ 得到剂量-反应曲线，强于二元 ON/OFF 的结论
3. `confidence` 直接进入主公式，实现者不会漏掉
4. **`level` 为 `unknown` 时 `confidence` 记为 0，故 `λ_eff = 0`**，系统自动退回不做个性化，无需额外分支

主方法用**软加权**而非硬过滤；硬过滤保留作 ablation。

### 3.5 C3 KG 扩展候选的计分

KG 邻居扩展会引入原检索未召回的候选。若为它们单独设计一个 KG 分数，将面临与 3.4 相同的量纲问题，且该分数难以校准。

**统一规则**：

```text
KG Expansion 产出新候选
→ 全部候选（原有 + 新增）重新经过 BM25 / Dense 计分
→ RRF 融合
→ C4 Level-Aware Reranking
```

这样不引入任何新的分数尺度，KG 的作用被限定为**扩大候选池**，而非直接干预排序。

### 3.6 C2.5 Topic Resolution：移至检索后

原设计在检索**前**运行问题 Topic 分类器；早期版本曾直接删除该模块，导致 topic-level profile 无法被 C4 读取。现改为检索**后**基于 metadata 解析：

```text
Question
→ C2 Hybrid Retrieval
→ 读取 Top-K 命中 chunk 的 chapter / topic metadata
→ 投票或加权得到当前 topic 及其置信度
   ├─ 置信足够 → 读取该 topic 的 level
   └─ 置信不足 → 回落 global level 或 neutral（不做个性化）
→ C4 Level-Aware Reranking
```

优势：使用既有 metadata 而非新训练黑箱；失败时有明确降级路径。

**两点代价需在报告中说明**：

1. C4 现在依赖 C2 的检索质量——检索差则 topic 解析差，个性化作用在错误的 level 上
2. 「置信足够」的阈值是新参数，须在 Dev 上标定

**主实验使用单一 global level**（见 §4.5 与 §7.1），topic-level 作为扩展实验，以免在主对比中引入这一层耦合。

### 3.7 C5 Calibrated Abstention：输入信号全部为推理时可得

**关键约束**：`gold` 只能用于**标定规则**与**评价结果**，绝不可作为 test-time feature。系统在运行时无从知道自己是否命中了 gold，将其作为输入会造成标签泄漏。

输入信号：

```text
normalized top1 score
top1 与 top2 的分差（margin）
BM25 与 Dense 结果的一致程度
Topic Resolution 的 confidence
Top-K 证据是否来自多个互相支持的 chunk
问题与证据的语义覆盖度
        ↓
   abstain / answer
```

`margin` 尤其重要：top1 高但 top2 紧随其后意味着歧义，top1 高且明显领先才是可信命中。

Gold evidence 的合法用途仅限：

```text
在 Dev 上标定 abstention 规则
在 Test 上评价 abstention 结果
```

**BM25、Dense、Hybrid 各配置必须分别校准，不可共用阈值**（分数尺度不同，与 3.4 同理）。

指标必须成对报告：Abstention Accuracy 与 False Abstention Rate。只报前者的话，全部弃答也能拿高分。

### 3.8 检索索引选型

本项目语料规模（预计几千至几万 chunk）下：

- **使用精确搜索**（如 FAISS `IndexFlatIP`），不用 HNSW / IVF 近似索引
- 精确搜索无召回率损失，且少一组要调的参数（`M` / `ef_search`），也少一个报告中要解释的混淆因素
- 参考量级：7000 chunk × 1024 维 ≈ 29 MB，暴力搜索单次几毫秒
- 仅当语料达百万级才需近似索引，届时应加元数据过滤（按章节 / 主题预筛）

### 3.9 Dense 特有的两个坑

1. **查询指令前缀**：bge 系列查询侧需加固定前缀，Qwen3-Embedding 有对应 instruct 格式。不加会明显掉点。Fail Fast Pilot 中若某 embedding 表现异常差，先排查此项再下结论。
2. **API 数据治理**：若不允许语料外发第三方，dense 必须本地部署，GPU 由「最好有」变为硬需求。

## 4. B 层：学生画像完整设计

本层有两个初始化入口，二者只在初始化阶段不同，最终都产出同一份 profile，之后共用同一套 C 层流程。

### 4.1 统一画像格式

```yaml
student_profile:
  student_id: anonymous_or_internal_id

  # 主实验使用的全局水平
  global_level: intermediate
  global_confidence: 0.70
  global_source: self_report

  # 扩展实验使用的分主题水平
  topics:
    programming:
      level: advanced
      confidence: 0.86
      source: transcript
      last_updated: 2026-08-23
    statistics:
      level: beginner
      confidence: 0.70
      source: self_report
      last_updated: 2026-08-23

  learning_goal: exam_preparation
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `level` | `beginner` / `intermediate` / `advanced` / `unknown` | 供 C4 与 C6 共用 |
| `confidence` | 0–1 | **直接进入 C4 的 `λ_eff = λ × confidence`** |
| `source` | `transcript` / `self_report` / `diagnostic` / `interaction` | 用于画像来源的对比实验 |
| `last_updated` | 日期 | B3 更新时写入 |
| `learning_goal` | 见 §4.2 | 仅影响 C6 的 prompt，不影响 C4 |

**`unknown` 规则**：某个 topic 信息不足时置为 `unknown`，由学生补充或诊断测验填补，**不做推断**。`unknown` 对应 `confidence = 0`，因此 `λ_eff = 0`，系统自动退回中性排序——不需要在代码里写额外的分支。

**`global_level` 与 `topics` 的关系**：主实验只读 `global_level`（见 §4.5）。`topics` 仅在 C2.5 topic-level 扩展实验中被读取，且 C2.5 置信不足时回落到 `global_level`。

### 4.2 方案 B：学生自选（默认入口）

不依赖真实成绩，实施成本低，隐私风险小，且更容易做可复现的研究实验。**这是默认方案。**

```text
学生首次使用
    ↓
选择水平（全局，或按 topic）
    ↓
选择学习目标
    ↓
（可选）Diagnostic Quiz
    ↓
Initial Profile
```

**水平选择的两个层次**

最低成本版本，单一全局水平：

```text
Beginner / Intermediate / Advanced
```

扩展版本，按 topic 选择：

```text
Programming       Advanced
Mathematics       Intermediate
Statistics        Beginner
Machine Learning  Intermediate
Deep Learning     Beginner
```

**学习目标**（仅进入 C6 的 prompt，不参与 C4 的排序）：

- 快速理解概念
- 准备考试
- 学习实际应用
- 理解数学推导

**Diagnostic Quiz —— 降级为 demo-only**

原设计包含 5–10 题的诊断测验用于校准自评。本架构**将其降为演示功能，不做效度论证**，理由：

1. 它需要第四套独立题目（Dev / Test / Smoke / Diagnostic），构造成本高
2. 从心理测量角度，5–10 题估计能力档次的标准误很大，效度本身需要单独论证
3. **主实验使用固定 synthetic profile（§4.5），诊断测验对主实验零贡献**

若保留为演示功能，两条约束不可违反：

- 诊断题**不得来自正式 Test Set**
- 诊断过程**不得造成评估泄漏**

confidence 的取值约定：

```text
仅自选              → confidence ≈ 0.60,  source = self_report
自选 + 诊断测验     → confidence ≈ 0.80,  source = self_report + diagnostic
```

**系统不得强制覆盖学生的选择。** 若诊断结果与自选不一致，只提示、由学生确认：

> 你选择了 Advanced，但诊断结果更接近 Intermediate。是否采用系统建议？

**方案 B 的风险**

- 学生可能高估或低估自己的水平
- 单一全局 level 无法表达不同 topic 之间的差异
- 诊断测验过短会产生不稳定判断
- 诊断题若与评估集重叠会造成泄漏

### 4.3 方案 A：成绩单 / Academic Profile（可选入口）

**状态：降级为可选功能，非默认，且不建议投入主要人力。**

降级理由有两条，第二条是决定性的：

1. 真实成绩属于敏感个人信息，受伦理审批阻塞
2. **PRAG-EDU（Computer Applications in Engineering Education, 2026-01）已经发表了同一思路**——用学生历史课程成绩作为教学信号校准回答复杂度，并建了 250 条专家验证的 benchmark。本项目再做，最好的结果是复现，新颖性不成立

**启用前置条件（须全部满足，缺一即切换方案 B）**

- 客户确认确实需要成绩单
- 学生明确授权
- 隐私与伦理要求已确认
- 明确成绩单的访问者、存储期限与删除方式
- 原始成绩单不会未经许可发送给第三方 LLM 或 Embedding API

**流程**

```text
成绩单 / Academic Profile
        ↓
授权、隐私与伦理检查
        ↓
最小化字段提取（课程名称、成绩、完成时间）
        ↓
课程 → Topic 映射
        ↓
成绩标准化与加权
        ↓
Topic Proficiency Score
        ↓
Beginner / Intermediate / Advanced
        ↓
写入 profile（source = transcript）
```

**课程到 Topic 的映射**

采用透明的规则式加权估计器，**不在缺乏训练数据与人工标签的情况下训练黑箱分类器**。

```text
COMP1001 → Programming: 0.8
         → Algorithms:  0.2

DATA1001 → Statistics:   0.6
         → Data Science: 0.4
```

```text
Topic Score =
Σ（标准化课程成绩 × 课程与 Topic 的关联权重）
÷
Σ（课程与 Topic 的关联权重）
```

**阈值——先解决评分制归一化**

原设计给出的阈值假设百分制：

```text
0–49   → Beginner
50–79  → Intermediate
80–100 → Advanced
```

> **⚠ 这组阈值只在百分制下成立。** 遇到 GPA 4.0 制、英国等级制（First / 2:1 / 2:2）或其他等级制会直接失效。启用方案 A 前必须先定义**评分制归一化规则**，再谈阈值。最终阈值须经团队与客户确认。

**方案 A 的风险**

- 成绩单可能无法反映学生对某个具体概念的当前掌握程度
- 不同课程与评分制度之间可能不可直接比较
- 课程与 Topic 的关联权重带有人工判断，不可验证
- 真实成绩属于敏感个人信息
- 画像结果必须允许学生查看、纠正或拒绝使用

### 4.4 两方案对比

| 维度 | 方案 A：成绩单 | 方案 B：学生自选 |
|---|---|---|
| 初始画像来源 | 历史课程成绩 | 学生自我判断 |
| 默认地位 | 获批后的可选功能 | **默认主方案** |
| 隐私风险 | 高 | 低 |
| 伦理审批 | 可能需要 | 通常不需要 |
| 实现成本 | 中高 | 低 |
| 新颖性 | **低（PRAG-EDU 已做）** | 不主张新颖性，只作为实验载体 |
| 冷启动体验 | 可自动生成 | 需要学生选择 |
| 主要误差 | 成绩与具体概念掌握不一致 | 自我判断偏差 |
| 校准方法 | Diagnostic Quiz / Interaction | Diagnostic Quiz / Interaction |
| 下游 C 层架构 | 共用 | 共用 |

**架构含义**：方案 A 若最终不可行，只需关闭 Transcript Profile Builder，C 层与 D 层完全不受影响。

### 4.5 实验中如何使用画像

**主实验使用固定的 Synthetic Profile，不使用真实学生画像。**

```text
Synthetic Beginner Profile      global_level = beginner,     confidence = 1.0
Synthetic Intermediate Profile  global_level = intermediate, confidence = 1.0
Synthetic Advanced Profile      global_level = advanced,     confidence = 1.0
```

这样做的理由：变量可控、实验可复现，且把「画像来源是否准确」这个问题与「个性化机制是否有效」彻底解耦。§7.1 冻结矩阵中的三个 level，指的就是这三份固定画像。

**画像来源的比较另作独立小型 pilot**，不与主矩阵交叉组合：

| 实验 | 内容 |
|---|---|
| Profile Initialisation Pilot | 比较 transcript-based / 自选 / 自选 + diagnostic 三种来源产出的画像差异 |
| Longitudinal Simulation（可选） | 用 synthetic student trajectories 验证 B3 的 Mini Quiz 更新机制 |

两者都属于扩展实验，不进入 §7.1 的正式矩阵。

### 4.6 教育公平与逃生舱

本系统的核心机制是**根据水平标签系统性地调整学生能看到的证据类型**。这带来一个教育层面的风险，原设计文档的风险清单只覆盖了技术与隐私，遗漏了这一条。

**风险**：被标记为 Beginner 的学生将被系统性地屏蔽 `derivation` 与 `boundary` 类证据。教育心理学中有充分证据表明，低期望会产生自我实现效应。**方案 B 同样有这个问题**——学生自选 Beginner 之后，若无干预就再也接触不到进阶内容。

**必须实现的缓解措施**

1. 学生可**随时切换** level，切换立即生效
2. 提供**单次请求更深内容**的入口（例如「显示推导过程」），不改变画像即可获得 Advanced 档证据
3. 画像结果对学生**可见、可纠正、可拒绝使用**
4. **拒答（C5）与个性化（C4）不得叠加**成「因为你是 Beginner，所以这段不给你看」——C5 的判据只能是证据充分性，与 level 无关

**报告中须显式讨论这一风险及缓解措施。** 在教育 AI 的评审语境下，主动提出并处理它是加分项；回避则是明显缺口。

## 5. 贡献陈述的表述边界

以下三项是本项目相对**所选对比对象**的增量。表述必须限定范围，不可做全域声明。

**1. 与课程语料绑定的 char-level gold evidence 与独立检索评估**

**不可**写成「无先行工作具备 gold evidence」——KILT 等通用基准已提供人工标注的 gold provenance 并分别评价检索与下游结果。

**2. 拒答机制与双指标**

在上述教育 RAG 对比对象中均未见拒答设计。

**3. 个性化同时作用于 C4 与 C6，且两处可分离开关**

各对比工作只覆盖其中一侧。

## 6. 实现顺序

```text
阶段零  数据集准备
        A0：OpenStax 解析 + SciQ 对齐 + Dev/Test 章节隔离
        ← 这一层不完成，后面全部无法开始

阶段一  可跑通的最小系统
        A1 → A5 → C2(仅 Dense) → C6 → C7(固定 JSON)
        = LPITutor 那一套，工程最轻，即 baseline

阶段二  补齐评估能力
        D1 + D2(Answer-choice Accuracy) → 加 A4(BM25) → C2 升级为 Hybrid RRF

阶段三  个性化
        A2 + A3(试标→冻结→批标) → B1(方案 B) / B2 → C4 → D3

阶段四  可靠性
        C5(多信号拒答) → C8(引用完整性) → D4 + D5

阶段五  时间允许（保持扩展地位）
        A6 + C3(KG) → C2.5(topic-level) → B3 + D6
        → 仅在获明确授权后：B1 方案 A（成绩单入口）
```

**两个瓶颈**

- **A0 是总阻塞。** Evidence Alignment 的质量决定 D1 是否可信，须单独排人并做人工抽验。
- **A3 是个性化链的瓶颈。** 试标 → 冻结 → 批标必须在阶段三开始前走完。

**A1 定稿后才建索引。** 2 个 embedding × 2 档切块策略 = 4 套索引，解析清洗逻辑每改一次，4 套全部作废重建。

## 7. 实验矩阵与预算

### 7.1 冻结的实验矩阵

以下为唯一的正式矩阵，其他表述以此为准。三个 level 对应 §4.5 的三份固定 synthetic profile。

**实验一 · 个性化（主实验）**

```text
主模型 × 180 题 × 12 condition
（4 组合 × 3 level）
= 2160 次调用
```

**实验二 · 模型对比（满足官方对 Llama / Qwen / Gemma / GPT 的横向要求）**

```text
另 3 个模型 × 分层抽取 60 题 × 6 condition
（condition A 与 D × 3 level）
= 3 × 360 = 1080 次调用

主模型在这 60 题上的结果直接复用实验一，不重复调用
```

**合计**

```text
2160 + 1080 = 3240 次调用
≈ 3240 × 3300 token ≈ 1070 万 token
```

**设计理由**：个性化是本项目的研究重点，在主模型上做深；模型对比是官方要求的横向动作，在冻结配置的两端（plain RAG 与完整系统）上做广。二者目标不同，不必交叉全跑。

**不进入本矩阵的扩展实验**：Profile Initialisation Pilot、KG 专项实验、topic-level 扩展、Longitudinal Simulation（见 §4.5 与 §6 阶段五）。

### 7.2 评价分工

| 范围 | 数量 | 方式 |
|---|---|---|
| 全部答案 | 3240 | Answer-choice Accuracy、可读性指标、C8 引用完整性、D1 检索指标 |
| 人工盲评 | 主模型中分层抽 **360** | 六维盲评 + D3 水平适配 + D4 atomic claim |
| 双标注 | 上述 360 中的 **20%（72 份）** | 计算 Cohen κ / Krippendorff α |

分层抽样须覆盖各题型、各 level、各 condition，**抽样方案在开封 Test 前确定**。

按每份 5 分钟计，360 份约 30 小时，加 72 份双标约 6 小时，8 人团队可承担。

### 7.3 检索层不消耗 LLM token

| 模块 | LLM token |
|---|---|
| C1 查询处理 | 少量，单轮场景可跳过 |
| C2 / C2.5 / C4 / C5 | 零 |
| C3 KG Expansion | 零～少量 |
| **C6 + C7 生成** | **约占 95%** |
| C8 引用完整性 | 零（字符串匹配） |

单次问答约 2900 输入 + 400 输出 ≈ 3300 token。

### 7.4 五条节流措施

1. **检索侧调参完全不调用 LLM。** chunk size、embedding 选型、Top-K、融合权重、λ 全部在纯 retrieval 层调完。
2. **缓存检索结果。** 12 个 condition 实际只有 6 套检索结果（3 level × 2 开关）。
3. **用 token budget 而非固定条数。** 统一 1500 retrieved tokens。
4. **C8 用字符串匹配；claim verification 只在抽样上跑。**
5. **评估阶段关闭 C1。**

### 7.5 索引构建成本

```text
7000 chunks × 500 token = 350 万 token
× 4 套索引 = 1400 万 token 过 embedding 模型
本地 GPU：每套几分钟；CPU：慢一到两个数量级
```

一次性成本，但上游改动会导致全部重建——见 §6 的顺序约束。
