## 待定（按该解决的先后排）

架构设计本身以 `docs/系统架构与文献映射.md`（v1.3）为准。本节只记「还没定、且定不下来会挡住别人」的问题。

### 1. 语料是否正式冻结 —— 9/11 截止

OpenStax College Physics 2e 的解析器已合并（#96），SciQ 题目已进 main，W4 的检索与生成都跑在这套语料上。导师承诺的数据集仍未到。

**截止日 2026-09-11（W5 周五）**：到期未到就正式冻结在 OpenStax + SciQ，这一条转入「已定」。理由见上表——13 周装不下第二次 parser freeze。

冻结的前置是 B6（同输入同配置逐字节一致），目前 parser 没有任何测试覆盖这条。**B6 不过就不该建索引**：按基线 §6，2 个 embedding × 2 档切块 = 4 套索引，解析逻辑每改一次全部作废重建。

### 2. A3 Evidence Role taxonomy 何时冻结 —— 个性化链的瓶颈

六类角色（definition / example / comparison / application / derivation / boundary）在基线 §3.3 已设计但**未冻结**。冻结前要走完：抽 100–200 chunk 试标 → 检查类别是否严重不平衡 → 重点查 `comparison` 与 `application` 是否混淆 → 双标 20% 报 Cohen κ / Krippendorff α → 一致性不足则改定义重标。

**排期上有冲突需要解决。** 基线 §6 写明「A3 是个性化链的瓶颈，试标 → 冻结 → 批标必须在阶段三开始前走完」，但看板把 `#16`（A3 试标，M5）和 `#17`（C4 Level-Aware Reranking，M7）排在同一周（W5，9/07–9/13），两条 Issue 的 Dependency 字段都是空的。C4 的评分公式需要 `role_match(level)`，没有冻结的 taxonomy 就算不出来。

在 A3 冻结前，`EvidenceItem` 不加 `evidence_role` 字段（见 ADR-0001 的 2026-09-05 修订段）。

### 3. 评估集：从 10–15 条到 60 Dev + 180 Test

基线 §7.1 的实验矩阵是冻结的：主实验 180 题 × 12 condition，模型对比另抽 60 题 × 6 condition。`#81` 的验收要求是「先产出 10–15 条可溯源 gold，并评估通向 60 Dev + 180 Test 的路径」，Go / No-Go 尚未记录。

未定的是构造方式（人工出题，还是 LLM 生成后人工筛——后者快，但要防「照着某一段出题」使检索任务过于简单），以及章节与概念隔离的具体划分（防泄漏，`#81` 的验收条件之一）。

注：`CLAUDE.md` 里「30~50 条问答对」是旧数字，以基线 §7.1 为准。

### 4. C4 的 λ 扫描范围与 confidence 来源

评分公式已冻结（基线 §3.4）：

```text
λ_eff = λ × confidence
final = (1 − λ_eff) · norm(retrieval_score) + λ_eff · role_match(level)
```

未定：λ 的扫描点位（要能画出剂量-反应曲线，而不是二元 ON/OFF）、`confidence` 从哪个画像入口取值（基线 §4 的方案 A 成绩单 / 方案 B 学生自选）、`norm()` 用哪种归一化（BM25 无上界而 Dense 余弦在 0–1，这正是公式改成单旋钮的原因）。

这三个值目前在 `EvidenceBundle` 里没有落位，`run_provenance` 是最可能的容器但没有约定。`#17` 开工前要定。

### 5. 模型对比的执行前提

官方点名 Llama / Qwen / Gemma / GPT，基线 §7.1 已把范围冻结为「另 3 个模型 × 60 题 × 6 condition = 1080 次调用」，主模型结果直接复用不重跑。

未定：本地 GPU 能跑多大的模型（决定全本地推理还是混用 API）、API 额度、以及 embedding 对比的候选集合——**语料是英文，早期设想的中文 bge 系列不适用**，当前实现用的是 `all-MiniLM-L6-v2`。

### 6. 人工评分量表（T4）

基线 §7.2 已定评价分工：全量自动 3240 份，人工盲评分层抽 360 份，其中 20%（72 份）双标注计 Cohen κ / Krippendorff α，抽样方案须在开封 Test 前确定。

未定的是量表本身：D2 的六维取自 LPITutor，D3 要把 EduAdapt 的 grade-aware rubric 映射到本项目的三档 proficiency（基线 §8 标注「需映射，不可直接比较原始 benchmark 分数」）。按 `CLAUDE.md` 的方法论，这套标准要**早于实现**定下来（R9）。

### 7. 架构基线以哪一份为准 —— v1.3 还是闭环 docx

`docs/动态闭环个性化KG-RAG架构设计.docx`（2026-08-30）比 `docs/系统架构与文献映射.md`（v1.3，2026-08-26）晚四天，项目名 **Closed-Loop Adaptive KG-RAG Tutor** 和看板的 "KG Loop" 视图都出自它，但它没进 `CLAUDE.md` 的文档索引，v1.3 也从未按它修订。

**两份不是对立的。** docx §10.1 明确「主实验保持静态」，§10.2 把动态闭环列为 30–60 个多轮场景的独立实验，「不与原 3240 次调用的完整矩阵交叉」——它保留了 v1.3 §7.1 的冻结矩阵。差异在优先级与组件：

- v1.3 §6 把 KG / C2.5 / B3 放在「阶段五 时间允许（保持扩展地位）」；docx §11 把 **Concept Check** 和 **Topic mastery 规则更新** 定为 P0，KG 先修/补救/进阶为 P1
- docx 新增四块 v1.3 完全没有的内容：三层动态上下文（§4）、Concept Check（§6）、Topic mastery 更新规则（§5.2）、教学模式与学生控制权（§9）
- docx §1 判定**成绩单方案（方案 A）已不可行**，而 v1.3 §4.3 仍保留它

**决定：以 docx 为准，v1.3 修订为 v1.4。** 但 docx §14 自己列了七条「冻结前需要团队确认」，未定之前不动契约层：

1. Concept Check 是否进正式演示的 P0 范围
2. 动态画像存本地 JSON / SQLite，还是仅保持单次会话
3. 每个 Topic 至少多少次作答后允许改变 level
4. KG 允许的关系类型、节点规模、人工验证比例
5. SciQ 练习池与正式 Dev/Test 的物理隔离方式
6. 自动生成题的验证门槛与失败时的降级策略
7. 动态闭环实验采用 30 还是 60 个多轮场景

第 2、3 条直接决定 `StudentProfile.topic_levels` 要改成什么形状——那是改现有字段的类型而非新增可选字段，按 `docs/interfaces.md` §「Changing a contract」第 2 条要 bump `schema_version`。
