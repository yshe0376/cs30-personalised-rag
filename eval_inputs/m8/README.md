## Correctness rubric review

`correctness-dev-rubrics-v0.1/` contains:

- `rubrics.draft.jsonl`: 154 Dev rubrics generated by the existing function.
- `rubric_review.jsonl`: the corresponding questions, references, evidence and pending status.
- `rubric_manifest.json`: exact source/output hashes and selected question IDs.

The source is the public generation handoff
[v2-m7-api-dev-20261026](https://github.com/yshe0376/cs30-personalised-rag/releases/tag/v2-m7-api-dev-20261026).
The converted Gold hash is
`235c92a15c14ef0416ac2ad262628c5876b9ebdde03c7f51438d10536a2509d5`.
The Dev generation-matrix hash is
`3c26abea35e60a4a1386952918fce595a5ca8d52aaec4bd059f21a868b2fd60d`.
Although the source Gold file contains 341 questions, the matrix selects only its
154 Dev questions. No Test rubric or generated answer is included in these files.

Review the criteria against the question and evidence before looking at generator
outputs. For term-identification questions, the plan permits the reference-derived
two-criterion draft with audit sampling. Refine calculation or multi-step questions
individually. Wording/type flags identify seven candidates for closer inspection;
they are hints, not a complete semantic classifier or approval.

Also consult the already committed, unreviewed concerns in
[`review_details.json`](../../docs/evaluation/eligibility-v1/review_details.json).
Eighteen of its Gold-answer concerns overlap this Dev set. In particular,
`sciq-train-00056` and `sciq-train-09086` need physics review. These flags are not
confirmed corrections; this branch does not edit Gold or silently substitute answers.
Changing Gold requires a separate provenance and generation-impact decision.

For each reviewed issue, record the question ID, decision, reviewer, evidence,
date and rubric change. Do not set `review_record_id` until a real review exists.
Editing `rubric_review.jsonl` alone does not approve or change a scoring rubric;
the scorer consumes `rubrics.draft.jsonl`. Issue a new version and refresh output
hashes whenever rubric content changes; retain the original draft.

Reproduce the files offline after downloading and extracting the handoff:

```powershell
$data = 'path/to/artifacts/m7-readiness-20261026'
python -m cs30.evaluation.open_answer_cli draft-rubrics `
  --gold "$data/dev-a741d960ae90-prepared/gold.jsonl" `
  --expected-manifest "$data/dev-a741d960ae90-run/expected_experiment.json" `
  --output-dir artifacts/evaluation/rubrics-dev-candidate
```

The command refuses existing output directories. It performs no provider calls.
Omit `--expected-manifest` only when intentionally preparing every answerable
open-ended question in the supplied V2 Gold file.

## Level profile and checklist review

The authoritative content remains
[`profile_checklist.draft.json`](../../docs/evaluation/level-profile-v1/profile_checklist.draft.json)
and its [human-readable explanation](../../docs/evaluation/level-profile-v1/README.md).
This branch does not change or duplicate that content.

Use the existing
[`review_record.template.json`](../../docs/evaluation/level-profile-v1/review_record.template.json)
from #197 as the single review template. This branch keeps no duplicate form.
The level-adaptation and level-discrimination judges require a reviewed, frozen
profile/checklist package; they cannot run while this input remains a draft.

The Leader checks the intended learner levels, the applicability rules and agreement
with the project plan. A distinct physics reviewer checks physical correctness,
assumptions and the anchor answers. Review both the criteria and examples; merely
running the code or seeing plausible scores does not complete this content review.
Record actual reviewer identities, decisions, timestamp with timezone, notes and
the real review-record reference. If the draft changes, rebind and repeat the review.

The existing exporter is reused after both genuine reviews approve:

```powershell
python -m cs30.evaluation.profile_authoring `
  docs/evaluation/level-profile-v1/profile_checklist.draft.json `
  --gold "$data/dev-a741d960ae90-prepared/gold.jsonl" `
  --review-record artifacts/evaluation/completed-profile-review.json `
  --output artifacts/evaluation/level-profile-v1.frozen.json
```

First copy the existing #197 template into the ignored local `artifacts/` directory
and fill it from the actual reviews, binding it to the current draft hash.
Do not pass the pending template as if it were approved.
The exporter rejects pending, stale or duplicate-identity approvals and writes a
hash-bound frozen package plus review receipt. No fake frozen package is provided.
Packaging the real review is an operational step; the user does not replace either
reviewer by running the export tool.

## Candidate runtime and next steps

The starting proposal is the previously smoke-tested `gemini-3.1-flash-lite`,
temperature 1.0, thinking `high`, and 8192 maximum output tokens. The numerical
defaults already exist in the merged adapter. They are not evidence of judge
quality, a confirmed budget, an immutable model version, or successful calibration.

1. Review and resolve rubric/reference concerns; confirm the generation data snapshot.
2. Prepare a small Dev correctness calibration with independent human reference
   ratings. It can proceed without learner profiles, using a confirmed budget.
3. Complete the existing profile/checklist review and export its frozen package.
4. Run the three judge tasks' Dev calibration and required validity checks, then
   record the accepted judge setup and thresholds with the Leader.
5. Complete eligibility calibration/review using the frozen profile. Then run the
   full Dev and independent-repeat scoring and produce the development report.
6. Formal Test generation/scoring follows the team's frozen experimental decisions.

Human reference ratings should be made without seeing the model's score first.
Inspect disagreements and raw supporting quotes, not only an aggregate accuracy.
Do not tune rubrics to favour a generator or label an offline validation as real
Gemini calibration. This branch does not run paid scoring or prescribe new validity
thresholds, delta, eligibility labels or comparison decisions.

## Eligibility integration from PR #205

The Evaluation code on this branch also implements plan section 12.1 item 7.
The adapter's existing eligibility-superset support is retained and tested against
missing/duplicate labels. Main adaptation uses `full + endpoint_only`; all-question
and `none` adaptation diagnostics are preserved separately. Paired contrasts are
also exported by eligibility subset without changing the all-question correctness
denominator. See the Evaluation README's "Eligibility subsets in the development
report" section for output files and coverage semantics. The committed labels and
profile approvals remain drafts; this integration does not approve them.
